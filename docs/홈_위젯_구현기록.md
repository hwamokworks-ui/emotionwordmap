**홈 화면 "오늘의 한 단어" · "요즘 많이 찾는 감정" 구현 기록**

> 이 문서는 홈 화면(`app/page.tsx`) 오른쪽 사이드바의 두 위젯을 실제 데이터 기반으로 바꾸는 과정과 그 안의 설계 판단을 기록한다.

## 1. 이전 상태 — 전부 하드코딩된 가짜 데이터

두 위젯 모두 실제 데이터를 전혀 보지 않고 화면을 채우던 목업이었다:
- "오늘의 한 단어"는 항상 "슬픔" 고정.
- "요즘 많이 찾는 감정"은 `{ id, label, count: '1,204명' }` 같은 배열이 코드에 그대로 박혀 있었다 — 인원수까지 전부 임의로 지어낸 값이었다.

사용자 질문("어떤 기준으로 된 거야?")에 대한 정직한 답은 "아무 기준도 없다"였고, 이를 계기로 실제 데이터 기반으로 교체했다.

## 2. 오늘의 한 단어 — 계절 × 시간대 기반 결정적 추천

발견 횟수 같은 실사용 집계 기준이 마땅치 않아 사용자에게 방향을 확인했다: **날짜(계절)와 시간대를 함께 고려한 추천**으로 정했다.

### 설계

- Asia/Seoul 기준으로 오늘 날짜(계절 계산용)와 현재 시각(시간대 계산용)을 구한다 — 서버가 어느 리전에 배포되든 한국 사용자 기준으로 계절·시간대가 어긋나지 않게 하기 위해서다.
- 계절 4종(봄/여름/가을/겨울) × 시간대 5종(새벽/아침/오후/저녁/밤) = 20개 조합마다 어울리는 감정 영역을 미리 매핑해뒀다(`lib/home-widgets.ts`의 `SEASON_TIME_REGION`). 예: 여름 오후→기쁨의 언덕(joy), 겨울 새벽→슬픔의 강(sad), 여름 밤→불안의 바다(sea, 후텁지근한 밤의 뒤척임).
- 해당 영역의 단어 목록을 가져와, `${날짜}-${시간대}` 문자열을 해시해 인덱스로 하나를 결정적으로 고른다. 그래서 같은 날 같은 시간대 안에서는 새로고침해도 같은 단어가 나오고, 시간대나 날짜가 바뀌면 다른 단어로 바뀐다.
- 실사용 데이터가 하나도 없어도(서비스 첫날이라도) 항상 결과가 있다 — 이 위젯은 사용자 행동 집계가 아니라 콘텐츠 자체(영역·단어)만 필요하기 때문이다.

## 3. 요즘 많이 찾는 감정 — 실데이터 우선, 부족하면 추천으로 채움

### 왜 RLS를 우회하는 함수가 필요한가

`user_word_discoveries`는 `auth.uid() = user_id` RLS 정책으로 보호돼 있어, 일반 anon 키로 조회하면 **로그인한 그 사용자 본인의 행만** 보인다. 홈 화면은 로그인 여부와 무관하게 "전체 사용자 중 이번 주 인기 감정"을 보여줘야 하므로, 일반 쿼리로는 애초에 집계가 불가능하다.

그래서 `supabase/migrations/0006_trending_words.sql`에 `security definer` 함수 `trending_word_counts(days_back, max_count)`를 새로 만들었다. 이 함수는 RLS를 우회하지만 **원본 행(누가 언제 발견했는지)이 아니라 집계된 숫자(단어 id·횟수)만 반환**한다 — 개인 식별 정보가 노출되지 않는 선에서만 RLS 우회 범위를 최소화했다.

### 부족분은 추천으로 채운다

집계 결과가 5개 미만이면(서비스 초기라 실사용 데이터가 적을 때 흔함) 고정 추천 목록(`RECOMMENDED_FALLBACK_IDS` — 슬픔·무력감·불안·후련함·그리움, 서로 다른 5개 지역)에서 모자란 자리만 채운다. 화면에는 실데이터 항목엔 실제 인원수를, 추천으로 채운 항목엔 가짜 숫자 대신 "추천"이라고 명시해 — 실제 통계처럼 보이는 거짓 정보를 만들지 않는다.

## 4. 버그 — emotion_words → emotion_regions FK가 3개라 조인이 모호했다

트렌딩 목록에 지역 색상(점 색깔)을 붙이려고 `emotion_words.select('..., emotion_regions(color)')`로 조인했더니 PostgREST가 에러를 냈다:

```
Could not embed because more than one relationship was found for 'emotion_words' and 'emotion_regions'
```

`emotion_words → emotion_regions` 사이에 FK가 3개 있었기 때문이다 — `region_id`(소속 지역), `edge_bias_region_id`(경계 단어 여백 조정용), 그리고 `emotion_regions.root_word_id`가 반대 방향으로 `emotion_words`를 참조하는 관계까지. PostgREST는 어느 관계로 조인할지 추측하지 않고 에러로 알려준다.

**해결**: 관계를 이름으로 명시했다.

```ts
.select('id, noun_form, region_id, emotion_regions!emotion_words_region_id_fkey(color)')
```

## 5. 남은 일

- `supabase/migrations/0006_trending_words.sql`을 Supabase 대시보드 SQL Editor에서 실행해야 실제 집계가 반영된다. 실행 전까지는 "요즘 많이 찾는 감정"이 전부 "추천"으로만 채워진 상태로 정상 동작한다(의도된 폴백).
